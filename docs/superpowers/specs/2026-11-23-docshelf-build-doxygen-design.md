# docshelf-build: Doxygen sites (design)

Date: 2026-11-23. Status: draft for the user's review. TODO 8.4.

## Intent

The user reads C and C++ API documentation online and often does not know
(or care) that Doxygen generated it. They want those sites offline in
docshelf the same way Sphinx and llms.txt sites already work: give
`detect` a docs URL, then `plan` and `build`. Near term: GLFW (used under
raylib) and wxWidgets (C++ docs, read to clarify the Python layer). Later:
embedded SDKs (Arm CMSIS components, Nordic nrfx / nRF Connect SDK).

## Goals

- A third site type, `doxygen`, in `docshelf-build`, chosen automatically
  by `detect` from a docs URL (a page in the site or its base).
- Typed entries (function, class/struct, macro, enum, ...) with links to
  the exact anchor, so docshelf `search` / `show` and `types` work as they
  do for Sphinx docvols.
- API pages in full; prose pages (Doxygen "related pages", markdown
  guides) as stubs that link to the live page, the same policy as Sphinx.
- Works on both index shapes seen in the wild:
  - **search index** (`search/searchdata.js` + `search/<category>_<n>.js`):
    GLFW, Arm CMSIS, OpenCV, gRPC (all checked 2026-11-22/23);
  - **no search index** (server-side search): wxWidgets, read through
    `menudata.js` and Doxygen's standard index pages.

## Non-goals

- Raspberry Pi Pico SDK: its site is Raspberry Pi's own conversion of
  Doxygen output, not Doxygen HTML (the user, 2026-11-23: ignore it).
- Doxygen **tagfiles** and Doxygen XML output (local builds). Possible
  later; not in this version.
- Sites that publish Doxygen through Sphinx (Breathe/Exhale: Zephyr,
  ESP-IDF, PyTorch C++): they serve `objects.inv`, which the `sphinx` type
  already handles. `detect` keeps preferring Sphinx.
- Merging several Doxygen sites into one docvol. A project split into
  components (CMSIS Core, Driver, RTOS2, DSP, ...) is built as one docvol
  per component (the user, 2026-11-23).
- Doxygen's server-side search (`search.php`, `search.idx`).

## Anti-goals

- Slowing down or burdening the sites: the same politeness as today (one
  request at a time, robots.txt on every host and redirect hop, retries
  with backoff). Planning must not fetch every content page.
- A docvol full of duplicate or junk pages (source-file listings,
  `*_8md.html` pages for markdown sources, directory pages, per-letter
  index pages themselves).
- New dependencies: stdlib only, like the rest of the skill.
- A change to the docvol on-disk format: `"format": 1` stays; docshelf
  needs no change.

## Constraints

- Public repo rules (AGENTS.md): no machine/account details; tests use
  hand-made fixtures, not copies of a project's generated files.
- `metadata.version` minor bump (new feature): 0.4.1 -> 0.5.0; script
  `VERSION` in `build_core.py` matches.
- `SKILL.md` stays a router: it gains one line for the new type and the
  description names Doxygen; the procedure goes in a new
  `BUILD-doxygen.md` read only for this type.
- Doxygen versions in the wild: 1.8.x to 1.12 at least (wxWidgets 1.9.1,
  nrfx 1.12.0). Themes such as doxygen-awesome restyle pages but keep
  Doxygen's element ids and classes.
- Some hosts sit behind bot protection (wxWidgets is on Cloudflare; plain
  fetches worked on 2026-11-23). A blocked fetch must fail clearly, never
  hang or loop.

## Approaches (chosen: A)

- **A. Search index first, index pages as the fallback** (chosen by the
  user, 2026-11-23). Read `search/*.js` when the site has it; otherwise
  read `menudata.js` and the typed index pages. Both readers produce the
  same entry list. Two readers to write and test, but the common case is
  a handful of compact files in a stable format.
- B. Index pages only: one reader for every Doxygen site, but it scrapes
  HTML whose layout varies by version and theme, and large sites split
  member indexes per letter (many requests); the search index goes unused.
- C. Tagfile first: richest data (argument lists, member-of), but few
  published sites serve one (none of the user's five did). Fits a later
  local-build option.
- Rejected: crawling from the front page without an index (slow, misses
  pages, untyped).

## Design

### Where it fits

The Sphinx path is the template. Today `plan` turns a list of
`InvEntry(name, role, priority, uri, dispname)` into a plan with
`build_plan.make_plan`, and `build_docvol.write_docvol` writes the index
from the same entries (`role_label` turns a role into the entry type).
The Doxygen readers produce `InvEntry` objects so that planning, the
fetch loop, stubs, archives-off, overrides (`--full`, `--stub`, `--all`,
`--reset`, `--base-url`) and the `classify`-free rule all work unchanged.

- Plan `kind`: `"doxygen"`; plan records which reader was used
  (`"index": "search"` or `"index": "menu"`) and the Doxygen version when
  a page states it (`<!-- Generated by Doxygen X.Y.Z -->`).
- `inventory_sha256`: a hash over the index files read, in a fixed order,
  so a rebuild notices a changed site the same way as for Sphinx.
- Project name and version for `derive_name` / meta: from the
  `#projectname` and `#projectnumber` elements of the front page (both
  are standard Doxygen ids; wxWidgets shows "Version: 3.2.13" in
  `#projectnumber`), falling back to the `<title>`.

### Roles and entry types

Roles use a `doxygen:` domain with the entry type as the kind, so
`role_label` returns it unchanged (a small mapping may be needed if
`role_label` lowercases). Prose pages use `std:doc` so the existing rule
makes them stubs.

| Doxygen category (search file / index page) | Role | Type shown |
|---|---|---|
| classes (incl. "Data Structures" in C mode) | `doxygen:Class` or `doxygen:Struct` | Class / Struct (struct/union when the page name starts `struct`/`union`) |
| namespaces | `doxygen:Namespace` | Namespace |
| functions | `doxygen:Function` | Function |
| variables | `doxygen:Variable` | Variable |
| typedefs | `doxygen:Type` | Type |
| enums | `doxygen:Enum` | Enum |
| enumvalues | `doxygen:Constant` | Constant |
| defines | `doxygen:Macro` | Macro |
| properties | `doxygen:Property` | Property |
| related ("Friends") | `doxygen:Function` | Function |
| groups ("Modules", "Topics", wxWidgets "Categories") | `doxygen:Module` | Module |
| files | `doxygen:File` | File |
| pages | `std:doc` | (page, stub) |
| any other category (concepts, events, sequences, dictionaries, ...) | `doxygen:<Label>` from `indexSectionLabels` | as labelled |

The names follow Dash's entry types where one fits (TODO 8.7 wants the
same type names across sources); "Constant" for enum values and "Type"
for typedefs are Dash's.

Entry names (my call, from the builder check): qualified only when the
scope is a class, struct, union or namespace (`cv::AsyncArray::_getImpl`,
`wxWindow::SetSize`); members whose scope is a file or a group (C
functions, macros, globals: Reader 1's third field `glfw3.h`, Reader 2's
`globals_*` link text) keep the bare name (`glfwCreateWindow`, never
`glfw3.h::glfwCreateWindow`); one entry per
(name, page, anchor). Overloads that share a name but differ by anchor
stay separate entries (docshelf already handles several entries with one
name). The display text keeps the signature when the index gives one
(e.g. `cv::_InputArray::_InputArray(const Mat &m)`), HTML entities
decoded.

### Reader 1: the search index

Checked formats (GLFW, CMSIS, OpenCV, gRPC, 2026-11-22/23):

- `search/searchdata.js` defines `indexSectionsWithContent`
  (category number -> string of first letters present),
  `indexSectionNames` (number -> file prefix: `all`, `classes`,
  `functions`, ...) and `indexSectionLabels` (number -> label shown).
- One file per category and letter: `search/<name>_<i>.js`, where `<i>` is
  the letter's position in that category's string **in lowercase hex**
  (GLFW `all_10.js` is the 17th letter, "m"; `all_a.js` the 11th).
- Each file is `var searchData=[ ... ];`, a JS array of
  `['<key>_<n>', ['<display name>', ['<url>', <flag>, '<scope or signature>'], ...]]`.
  URLs are relative to `search/` (`../group__window.html#ga...`). Strings
  are single-quoted with HTML entities (`&amp;`, `&lt;`).

Rules:

- Read the per-category files, never `all_*`: the category gives the
  type, and `all` mixes in section headings of prose pages.
- Parse with a small purpose-built tokenizer for this literal subset
  (nested arrays, single-quoted strings with backslash escapes, integers),
  not `eval` and not a general JS parser. Anything else is a parse error
  for that file: warn and continue with the others.
- Older Doxygen (1.8.x) named the files by the letter's character code
  (`all_61.js` for "a") and may differ slightly in entry shape. The reader
  should support it if a test site can be found; otherwise detect the
  shape, report "unsupported search index format" and fall back to
  Reader 2.
- File count: categories x letters, typically 50-300 small files. Fetched
  with the existing `Source` (politeness, robots.txt, retries).
- Optionally cache the index files under `built-src/NAME/index/` so a
  re-plan does not refetch them (the llms.txt path already keeps raw
  pages in `built-src/`); the builder decides.

### Reader 2: `menudata.js` and the index pages

Used when `search/searchdata.js` is missing (404) or unusable.

- `menudata.js` (Doxygen 1.8.12+, checked on wxWidgets 2026-11-23) holds
  `var menudata={children:[{text:"...",url:"...",children:[...]}]}`: the
  top menu with every index page, its typed tabs
  (`functions_func.html`, `functions_vars.html`, `globals_defs.html`, ...)
  and per-letter subpages (`functions_a.html#index_a`,
  `globals_defs_e.html#index_e`). Same tokenizer, plus unquoted keys.
- Pages to read, by menu URL (drop the `#index_x` fragment, dedupe):
  - class list: `annotated.html` (names and links; `classes.html` is the
    same set as an alphabetical index);
  - namespaces: `namespaces.html`; files: `files.html`;
  - groups: `modules.html` or `topics.html`; pages: `pages.html`;
  - typed member indexes: `functions_<kind>[_<letter>].html`,
    `globals_<kind>[_<letter>].html`,
    `namespacemembers_<kind>[_<letter>].html`, where `<kind>` is `func`,
    `vars`, `type`, `enum`, `eval`, `rela`, `prop`, `defs` (macros, in
    `globals` only). The untyped "All" pages (`functions.html`,
    `functions_a.html`, ...) are skipped when typed tabs exist.
- Member index pages list `name : Owner` items whose links point at the
  member's page and anchor (`classwx_window.html#a...`). The parser takes
  each link inside the page's `div.contents`, the text before it as the
  name, the link text as the owner; it ignores the letter navigation.
- If `menudata.js` is missing too, try the fixed names above
  (`annotated.html`, `functions_func.html`, ...) and read the letter
  links from each page's own navigation.
- Request count: wxWidgets 3.2 lists about 150 index pages; each is one
  request at the existing politeness rate. `plan` prints how many it will
  fetch before it starts.

### Planning rule

- A page is **full** when at least one entry other than its own
  `File`/`Module`/`Namespace` heading entry points at it (that is, it
  documents members), or it is a `Class`/`Struct` page.
- A page is a **stub** when it has only `std:doc` entries (prose pages).
- Never planned (dropped before the plan): the index pages themselves,
  `*_8md.html` / `*_8dox.html` pages (markdown/dox source listings),
  `dir_*.html`, `*_source.html` (source listings), `graph_legend.html`,
  `deprecated.html` / `todo.html` / `bug.html` lists.
- `File` pages that only list members documented elsewhere become stubs
  by this rule; a header page that documents its own macros stays full.
- Group (`Module`) pages hold most of the API in C libraries (GLFW, CMSIS,
  nrfx): they are full whenever members point into them, which is the
  normal case.
- Overrides work as for Sphinx (`--full 'group__*'`, `--stub PAT`).

### Fetching and content

- `build` fetches full pages exactly as for Sphinx (no archive: Doxygen
  sites offer none).
- `build_html.main_content` needs Doxygen's content element. Add
  selectors, before the generic `body` one: `div.header` (title block,
  kept) and `div.contents`. Doxygen pages have no `main`/`article`
  element, so without this the whole page (menus, tree, search box) would
  be stored. The builder decides how to join header + contents (e.g. take
  `div#doc-content` when present, else the two divs).
- Strip Doxygen chrome inside the content: the "More..." links, the
  include-dependency and collaboration graph images (images already
  become their alt text; drop graph `<map>`/`<area>`), the
  "Generated by" footer, and the dynamic-section toggle arrows.
- Anchors: Doxygen member anchors (`a8a87f6...`, `ga...`) are already
  valid ids; `anchor_id` keeps them.

### detect

- After the Sphinx and llms.txt checks fail, look for a Doxygen site:
  from the given URL's folder (and its parent once, for a page URL deep in
  the site), fetch `search/searchdata.js`, then `menudata.js`.
  - `searchdata.js` with `indexSectionNames` -> `type: doxygen`,
    `index: search`.
  - else `menudata.js` with `var menudata=` -> `type: doxygen`,
    `index: menu`.
- Prefer Sphinx, then llms.txt, then Doxygen; print the others as `also:`
  lines as today. A Breathe site therefore stays `sphinx`.
- `source:` is the Doxygen output folder URL (the folder holding
  `search/` / `menudata.js`). Local folders work the same way (an HTML
  output folder on disk).
- `read: BUILD-doxygen.md`.

### Naming

- `derive_name` from the project name (`glfw`, `wxwidgets`); the user
  passes `--name cmsis-core` etc. for component sites. The DevDocs name
  check stays.

### Files to change (expected)

- New `scripts/build_doxygen.py`: the tokenizer, both readers, the
  category -> role map, the page filters. Returns `(header, entries)` like
  `parse_inventory`.
- `build_detect.py`: the Doxygen probe and `DOCS["doxygen"]`.
- `build_fetch.py` / `Source`: an `index_files()` (or similar) method to
  fetch `search/*` and index pages; no new network rules.
- `build_plan.py`: `kind: "doxygen"`, the page filters and the full/stub
  rule (or a parameterised `make_plan`); `summarize` shows the reader used
  and entry counts per type.
- `build_html.py`: Doxygen content selectors and chrome stripping.
- `build_docvol.py`: `role_label` for the `doxygen` domain if needed.
- `docshelf_build.py`: dispatch `plan`/`build` on the detected kind.
- `BUILD-doxygen.md` (new), `SKILL.md` (router line, description names
  Doxygen), `tests/test_docshelf_build.py`, AGENTS.md skill notes.

### Tests

- Hand-made fixtures (not copies of a project's files): a tiny Doxygen
  output tree with `searchdata.js`, a few `<category>_<hex>.js` files
  (including one past index 9 to pin the hex naming), class, group, file
  and prose pages; and a second tree with `menudata.js` and typed index
  pages (with per-letter subpages) but no `search/`.
- Tokenizer: escapes, entities, nested arrays, unquoted keys, a malformed
  file (warns, others still read).
- Rule: class/group pages full, prose pages stubs, `_8md`/`dir_`/index
  pages dropped, overrides.
- detect: search-index site, menu-only site, Breathe-like site with
  `objects.inv` (stays `sphinx`), neither (exit 3).
- main_content on a Doxygen page keeps the title and member docs and
  drops the menu, tree, search box and footer.
- Real-site quirks, covered by fixtures whatever the trials show (my call,
  from the builder check): a bot-protection HTML page served with status
  200 where a `.js` index file is expected fails clearly (a "not a Doxygen
  index file, the site may be blocking automated requests" error, never
  parsed as empty); a member link lands on the member: Doxygen writes an
  empty `<a id="...">` just before each member's `memtitle` heading, and
  that id must survive `main_content` so `show NAME:PAGE#anchor` finds it;
  a doxygen-awesome page (extra wrapper divs) gives the same content.
