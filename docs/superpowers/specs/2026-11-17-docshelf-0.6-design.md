# docshelf 0.6: dependency suggestions, sturdier anchors, lookup defaults

Short design (approved by the user, 2026-11-17). TODO.md items 1.5, 2.2
and 5.1 of the docshelf section. Version 0.5.0 -> 0.6.0 (new features in a
skill with scripts).

## Intent

- 1.5: an agent starting work in a project should learn which docvols fit
  the project (and which versions) without guessing from memory.
- 2.2: `show` on a docset REF should land on the right section for the
  anchor forms Dash docsets actually use, and degrade to the whole page.
- 5.1: projects should be able to say, once, which documentation lookup
  tool agents prefer; when they haven't, the agent asks the user once and
  never again.

## Approaches

- 5.1, where the "already asked" record lives (the user picked B):
  - A. The project's `.docshelf.json`: per project, but creates that file
    in projects without one.
  - **B. The project's AGENTS.md / CLAUDE.md only**: every answer,
    "no preference" included, becomes a short section there; its presence
    is the record. No extra file.
  - C. User-wide state in docshelf's notes folder: lost in cloud
    containers, ignores per-project differences.
- 1.5: print only (agent or user edits `.docshelf.json`) vs. a `--write`
  flag. Print only (my call): docshelf doesn't write project files, and the
  agent can edit JSON.
- 2.2: one way: extend the existing HTML-to-blocks parser and section
  slicer; no separate anchor resolver.

## 1.5 `suggest`

- New command `suggest` (and MCP tool `suggest`): scans the project root
  and one level down for monorepos (`packages/*`, `apps/*`, direct child
  folders holding a manifest). No deep walk. The root is the folder
  holding `.docshelf.json` when that file was found walking up from the
  current folder and is the current folder or in the same git work tree;
  otherwise the current folder. `suggest` notes the folder it scanned
  (ruling after the final review, 2026-11-17: an ancestor or fallback
  project file made it scan siblings or `$HOME`).
- Files read (Tier 1, the user, 2026-11-17). The file's presence implies a
  tool or language; its contents give libraries and versions:
  - `package.json`: dependencies, devDependencies, `engines.node`; implies
    javascript (node only when `engines.node` or a node version file).
  - `pyproject.toml` (PEP 621 `dependencies`, `optional-dependencies`,
    `requires-python`; Poetry `tool.poetry.dependencies` incl. `python`),
    `requirements*.txt`: implies python. `tomllib` (3.11+); on older
    Python the TOML files are skipped with a note.
  - `CMakeLists.txt`: cmake, `find_package(Name ...)`,
    `CMAKE_CXX_STANDARD` -> cpp.
  - `Cargo.toml`: rust, crate names.
  - `go.mod`: go, the `go 1.NN` line.
  - `Gemfile`: ruby, `gem "name"`, `ruby "X.Y"`.
  - `composer.json`: php, `require` / `require-dev` (`vendor/name`).
  - `Dockerfile`: docker, `FROM image[:tag]`.
  - `docker-compose.yml`, `docker-compose.yaml`, `compose.yml`,
    `compose.yaml`: docker, `image:` lines (line patterns, no YAML parser).
  - `.nvmrc`, `.node-version`, `.python-version`, `.ruby-version`,
    `.tool-versions`: the language and its exact version.
- Matching: normalize names (lowercase, PEP 503 `-_.` folding, strip npm
  scope `@types/`, `vendor/` prefix, image tags/registries), then match
  against DevDocs families, slugs and aliases from the cached `docs.json`
  and against installed docsets (names and families). A small mapping table
  covers known non-obvious names (`react-dom` -> react, `@types/node` ->
  node, `laravel/framework` -> laravel, `postgres` image -> postgresql,
  ...). Versions pick the matching docvol version when one exists
  (`python~3.12`), else the family's newest with the version noted.
- Network: none by default; uses the cached `docs.json` when present. If no
  DevDocs list is cached, match installed docvols and docsets only and say
  that `sources` (network) would find more. (Builder's call whether a
  `--refresh` flag is worth adding.)
- Output: one line per suggestion with status (`installed`, `docset`,
  `available`) and where it came from (`cmake (CMakeLists.txt)`,
  `python~3.12 (.python-version)`), then a ready-to-paste `"docvols"`
  list of installed and available names. `--json` for machine output.
  Print only; docshelf never writes `.docshelf.json`.
- Unmatched dependency names are not listed (most libraries have no
  docvol); a count is.
- Tier 2 files (Pipfile, environment.yml, deno.json, pubspec.yaml, mix.exs,
  meson.build, vcpkg/conan, CI workflows) and Java build files are out of
  scope and not added to TODO (the user, 2026-11-17).

## 2.2 Sturdier anchors

- `name=` is an anchor on any tag, not only `<a>`.
- Empty Dash anchors (`<a name="//apple_ref/..." class="dashAnchor">`,
  `//dash_ref...`) attach to the next emitted block (heading or other);
  several stacked anchors all attach. Lock with tests.
- A `<details>` element whose `id`/`name` is the anchor is one section,
  ending at its `</details>` (summary included).
- Anchors percent-encoded once or twice resolve (both in the REF and in
  the page).
- Not found: whole page with the existing note (unchanged).
- Tests from markup patterns of real docsets; consult
  andreas-mausch/docset-mcp's tested-docsets table and ZDocsetMCP for the
  patterns to cover.

## 5.1 Lookup defaults

- New `references/lookup-defaults.md`. `SKILL.md` gets one line: read it
  only when the project's AGENTS.md and CLAUDE.md (and the user's global
  ones the agent already sees) say nothing about which tool to use for
  documentation lookups.
- The file tells the agent to:
  1. List the lookup tools it actually has (docshelf, docs MCP connectors
     such as Context7 or Microsoft Learn, web search).
  2. Ask the user once: docshelf by default, another tool by default, an
     order to try them in (only with two or more), or no preference.
  3. Write the answer under `## Documentation lookups` in the project's
     AGENTS.md if it exists, else CLAUDE.md, else ask which to create. Every
     answer is written, "no preference" as one line; that section is the
     record that the question was asked, so it is never asked again.
- The paste-in snippet (~10 lines, harness-neutral, teaching the lookup
  habit: search before answering from memory, quote the docs, pin the
  version) lives in that file, for the "docshelf by default" answer and for
  people adding it by hand.
